# ARCWorks Restaurant Suite Roadmap — 2026-08-06

## Direction

The project is now intentionally focused on a dependable, deterministic
restaurant system before further UI polish or AI integration.

### Active product scope

1. Waiter → Kitchen → Manager → Admin/Owner
2. Manager/Admin → independent-item Inventory
3. Manager → Staff Schedule → Reports
4. Operational alerts after workflow acceptance

### Explicitly deferred

- AI assistant and command gateway integration
- Recipe definitions, yields, costing, and ingredient consumption
- Natural-language SQL and autonomous actions
- Voice control and network GPU aggregation
- Multi-tenant hosting and VM-per-restaurant expansion
- Major visual redesign work until workflow acceptance is stable

AI source, benchmark evidence, contracts, and the isolated laboratory remain
preserved for a future version. The current application uses `AI_HOLD=true`,
does not register the gateway client, and is not attached to the private AI
network. See [`AI_HOLD.md`](AI_HOLD.md).

## Current position

The core application already contains role-based ordering, kitchen status flow,
cashier/payment flow, reporting, manual inventory controls, negative-stock
handling, Admin/Owner overrides, receiving, witnessed count reconciliation,
staff scheduling, backups, recovery tooling, monitoring, Docker deployment,
and Cloudflare routing.

The remaining work is acceptance and operational hardening, not another large
feature expansion.

## Next implementation sequence

### Step 1 — Freeze the workflow contract

- Write down the allowed waiter, kitchen, management, inventory, schedule, and
  report actions.
- Confirm role ownership and forbidden transitions.
- Do not add convenience features that bypass the existing audit and reversal
  rules.

**Status: complete.** The frozen role, state, inventory, schedule, reporting,
route, and acceptance contract is recorded in
[`WORKFLOW_CONTRACT_2026-08-06.md`](WORKFLOW_CONTRACT_2026-08-06.md).

### Step 2 — Review and implement the revised four-role workflow

- Review [`REVISED_WORKFLOW_DRAFT_2026-08-06.md`](REVISED_WORKFLOW_DRAFT_2026-08-06.md).
- Confirm the separate Manager role, kitchen return/resubmission path, standard
  timer ownership, item-based preparation target, and Manager live-only/
  historical-data boundary.
- The clarified rules are recorded in the frozen contract. Persisted timer
  settings, timer deadlines, bounded extensions, and manager live-order data
  are implemented; browser acceptance remains the next gate.

### Step 3 — Run deterministic workflow acceptance

- Use realistic but synthetic restaurant data first.
- Test the full waiter → kitchen → management path with simultaneous role
  sessions where possible.
- Include cancellation, amendment, payment, duplicate submission, stale page,
  and reconnect scenarios.

### Step 4 — Accept inventory with human gates

- Import or enter approved independent inventory items and units.
- Record witnessed opening counts.
- Verify receiving, physical counts, negative-stock behavior, Admin/Owner
  override, and correction/reversal evidence.
- Keep recipes and automatic ingredient deduction disabled.

### Step 5 — Accept schedule and reporting behavior

- Verify non-overlapping shifts, attendance ownership, corrections, date
  boundaries, role restrictions, and CSV/report output.
- Test empty periods, future periods, month boundaries, and timezone-sensitive
  dates.

### Step 6 — Complete one controlled recovery drill

- Use the existing backup staging and Restic repositories.
- Restore databases into an isolated destination.
- Recreate the application with the restored data.
- Confirm login, order history, inventory history, schedules, reports, and
  audit records remain available.
- Preserve the complete drill log before declaring recovery accepted.

### Step 7 — Implement and accept operational alerts

- Implement only after the revised core workflow is accepted.
- Start with codes `85`, `86`, `68`, `100`, and `200`.
- Keep `50` and `95` out of scope.
- Allow additional code definitions only through Admin/Owner configuration.

### Step 8 — Prepare supervised beta

- Freeze the staging image and configuration.
- Confirm domain/tunnel routes and allowed hosts.
- Confirm monitoring alert ownership and backup prompt behavior.
- Load restaurant-approved menu, staff, role, tax, payment, and inventory data.
- Run a limited supervised beta before any public rollout.

## Release gates

The project should not move to final UI work or public beta until all of these
are true:

- [ ] Waiter, kitchen, and management workflow accepted by role.
- [ ] Inventory data and opening counts approved by a human owner.
- [ ] Negative stock, Admin/Owner override, receiving, counting, and reversal
      paths accepted.
- [ ] Schedule, attendance, and reporting boundaries accepted.
- [ ] Backup restore drill completed and documented.
- [ ] Staging configuration and secret ownership frozen.
- [ ] Monitoring and incident response ownership assigned.
- [ ] External audit findings have a documented disposition.
- [ ] UI changes tested against the now-stable workflow contract.

## Current risk posture

### Controlled

- AI cannot affect the active application while the hold is enabled.
- Core state changes remain deterministic and authorization-checked.
- Backup and recovery procedures are documented and testable.
- The branch and draft PR workflow protects `main` from unverified changes.

### Still requiring evidence

- Real staff simultaneous-use acceptance.
- Restaurant-approved opening data and operating policies.
- A completed restore drill from the selected production-like backup.
- Final staging/tunnel/monitoring ownership and beta configuration.
- Browser and visual acceptance after the workflow contract is frozen.

## Decision rule

When a proposed feature increases cross-module coupling or requires a new
external service, first ask whether it is necessary for the three active
workflow groups. If not, record it as deferred rather than allowing it to delay
the deterministic core.
