# ROMS Roadmap — 2026-08-02

## Current position

The non-AI ROMS core is substantially implemented: role-based ordering,
kitchen flow, cashier/payment flow, reporting, manual independent-item
inventory, negative-stock controls, manager override evidence, receiving,
count reconciliation, and waste/spoilage approval workflows exist.
The Docker application, MariaDB, monitor, private Ollama lab, and Cloudflare
tunnel are operational. Stress, adversarial, real-MariaDB, and browser coverage
exist, but real restaurant beta acceptance remains outstanding.

The AI path now has a feature-gated Assistant screen and an implemented
read-only function boundary. The command gateway and model still have no
database credentials or write authority. ROMS alone authenticates users,
applies role/ownership rules, queries MariaDB, and formats returned facts.

## Current move — AI Phase 1 acceptance

The deterministic boundary is implemented:

1. Twelve approved functions cover exact menu, inventory, order, and permitted
   summary reads.
2. Signed-in ROMS authorization and current database state govern every read.
3. The model receives bounded catalogs and proposes only a typed function.
4. Invalid, ambiguous, unsupported, or unavailable interpretation fails closed.
5. ROMS formats the factual response and audits sanitized function execution.
6. The feature remains disabled by default.

The next gate is contained container-model and browser acceptance followed by
the adversarial/multilingual corpus. See `docs/AI_FUNCTIONS.md`.

This is the next implementation gate. AI write proposals, including inventory
receiving, are excluded from the Phase 1 protocol and user-facing assistant.

## Remaining gates

| Gate | Deliverable | Exit evidence | Relative effort |
|---|---|---|---|
| 1. Read-only contract | Approved tool schemas, authorization map, audit fields, threat cases | Complete: contract and denial tests | Complete |
| 2. Grounded service | ROMS read-only query adapter plus deterministic validation | Complete: in-memory and disposable MariaDB tests | Complete |
| 3. Assistant integration | Feature-flagged staging UI with timeouts and safe fallback | Implemented; contained model and browser spot-check passed, full corpus pending | Small |
| 4. Adversarial acceptance | Multilingual ambiguity, prompt injection, stale data, permission, timeout, and concurrency corpus | Zero unauthorized actions; known-answer and clarification thresholds met | Medium–large |
| 5. Operational readiness | Metrics, retention policy, model rollback, backup/restore and offline behavior | Runbook plus recovery drill | Medium |
| 6. External audit and beta | Independent security/architecture review and simultaneous staff acceptance | Signed findings disposition and restaurant beta approval | Schedule-dependent |

A realistic estimate is five engineering gates before a guarded AI pilot, plus
the external-audit/beta gate. The core restaurant system does not need to wait
for AI: staging acceptance with real staff and restaurant-approved opening data
can proceed independently.

## Production blockers that AI does not solve

- Restaurant validation of opening inventory, menu pricing, tax,
  discounts, refund rules, staff roles, and operating hours.
- Simultaneous waiter/kitchen/cashier acceptance by real users.
- A production restore drill from the selected backup, not merely backup
  creation.
- Final staging-versus-production configuration, secrets, TLS/tunnel access
  policy, monitoring alerts, and incident ownership.
- Explicit sign-off on the remaining external-audit findings.

## Deferred work

- Arbitrary natural-language SQL.
- Direct AI inventory receipts, discounts, refunds, price changes, payroll, or
  deletion actions.
- Automatic model selection exposed to staff.
- Network GPU aggregation.
- Voice control until the text path passes the same authorization and safety
  gates.
- Recipe definitions, yields, costing, consumption, and menu-to-ingredient
  mappings. These are outside the approved release scope.
