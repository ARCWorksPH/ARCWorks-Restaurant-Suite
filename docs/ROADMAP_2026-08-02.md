# ROMS Roadmap — 2026-08-02

## Current position

The non-AI ROMS core is substantially implemented: role-based ordering,
kitchen flow, cashier/payment flow, reporting, inventory consumption and
reversal handling, negative-stock controls, manager override evidence,
receiving, count reconciliation, and waste/spoilage approval workflows exist.
The Docker application, MariaDB, monitor, private Ollama lab, and Cloudflare
tunnel are operational. Stress, adversarial, real-MariaDB, and browser coverage
exist, but real restaurant beta acceptance remains outstanding.

The AI work is still an isolated laboratory. It has no production database
credentials, no user interface, and no authority to execute ROMS commands.
Benchmark 3 retained two CPU-only finalists: `qwen2.5:3b` as the balanced
default and `qwen3:4b-instruct` as a factual/read-only challenger.

## Recommended next move — AI Phase 1 read-only contract

Before adding an assistant screen, define and test the deterministic boundary
between ROMS and the model:

1. Add approved read-only function contracts for exact menu price, inventory
   balance, recipe/yield calculation, order-status lookup, and permitted report
   summaries.
2. Query those functions through ROMS application services using the signed-in
   user's existing authorization. Do not give the model SQL or a database
   connection string.
3. Give the model only the minimum returned facts needed for one request.
4. Require clarification when item, quantity, unit, order, date range, or user
   intent is ambiguous.
5. Validate the final response against the function result before displaying
   it, and record model tag, request category, tool result, latency, refusal,
   and failure without storing unnecessary private conversation text.
6. Keep the feature disabled by default and expose it first to administrators
   in staging.

This is the next implementation gate. `InventoryReceive` may remain a lab
proposal for testing, but it must not be connected to the Phase 1 user-facing
assistant.

## Remaining gates

| Gate | Deliverable | Exit evidence | Relative effort |
|---|---|---|---|
| 1. Read-only contract | Approved tool schemas, authorization map, audit fields, threat cases | Contract/unit tests and documented denial cases | Small |
| 2. Grounded service | ROMS read-only query adapter plus deterministic validation | Disposable MariaDB integration tests | Medium |
| 3. Assistant integration | Feature-flagged admin/staging UI with timeouts and safe fallback | Browser tests, no direct DB/model mutation path | Medium |
| 4. Adversarial acceptance | Multilingual ambiguity, prompt injection, stale data, permission, timeout, and concurrency corpus | Zero unauthorized actions; known-answer and clarification thresholds met | Medium–large |
| 5. Operational readiness | Metrics, retention policy, model rollback, backup/restore and offline behavior | Runbook plus recovery drill | Medium |
| 6. External audit and beta | Independent security/architecture review and simultaneous staff acceptance | Signed findings disposition and restaurant beta approval | Schedule-dependent |

A realistic estimate is five engineering gates before a guarded AI pilot, plus
the external-audit/beta gate. The core restaurant system does not need to wait
for AI: staging acceptance with real staff and restaurant-approved opening data
can proceed independently.

## Production blockers that AI does not solve

- Restaurant validation of opening inventory, recipes, menu pricing, tax,
  discounts, refund rules, staff roles, and operating hours.
- Simultaneous waiter/kitchen/cashier acceptance by real users.
- A production restore drill from the selected backup, not merely backup
  creation.
- Final staging-versus-production configuration, secrets, TLS/tunnel access
  policy, monitoring alerts, and incident ownership.
- Explicit sign-off on the remaining external-audit findings.

## Deferred work

- Arbitrary natural-language SQL.
- Direct AI inventory receipts, discounts, refunds, price changes, payroll, or
  deletion actions.
- Automatic model selection exposed to staff.
- Network GPU aggregation.
- Voice control until the text path passes the same authorization and safety
  gates.
